## 二、v1.3.0：倍速为什么"不好用"

### 现象（`cx-diag-2026-10-21T09-40-43.json`）

```
cfg.rate      = 1        ← 面板显示 1x
player.rate   = 2        ← 视频实际 2x
learnProgress = 159.15   ← 视频位置
learnDuration = 90.10    ← 服务端认的时长
```

日志里 17:39:28 / 17:39:55 / 17:40:18 三次切回 1x 全部无效，最后手动暂停。

### 根因 1：`rate = 1` 永远不会被写回（代码 bug）

```js
if (CFG.rate !== 1) Player.speed(CFG.rate);   // ← 旧代码
```

切到 1x 时这个条件为假，**什么都不做**。所以一旦上了 2x，就再也回不到 1x，面板却照样显示 1x。这是"倍速调节失灵"的直接原因。

修法：去掉短路，任何目标值都写；点击后**立即**写，不等主循环。

### 根因 2：倍速本身在这个平台上不省时间（机制问题）

平台自己的源码（`web.ea79ebb4.js`）：

```js
this.activeList.isLearned.learnDuration += (now - enterTime) / 1000;   // 真实时钟
if (learnDuration > durationSec) learnDuration = durationSec;          // 上限
this.activeList.isLearned.learnProgress = Math.max(learnProgress, getCurrentTime());
```

`learnDuration` 按**真实秒**累加，`learnProgress` 跟视频位置走。2x 播完一节 277s 的视频，进度到 277，真实时长只有 138 —— 正好一半，与诊断数据 `90.10 / 159.15` 完全吻合。

历史完成节点里，`learnDuration / durationSec` 最低的两个是 **0.945**（1.4）和 **0.973**（2.2），而上一轮 `3.3` 只有 0.812 时是 `false`。所以判定线大致在 **0.9 附近，且看的是真实时长**。

**结论：真实时长只能靠挂机时间堆，倍速改变不了总墙钟。** 277s 的课，1x 要 277s，2x 也要约 255s（还得回头补 117s）。倍速只改变"视频循环几遍"，不改变"要挂多久"。

### v1.3.0 的应对

| 机制 | 行为 |
|---|---|
| 倍速立即生效 | 点击 / `__CX.rate(n)` 立刻写入，暂停状态也生效 |
| 双通道写入 | `inPlayer.setSpeed()` + `video.playbackRate`，任一成功即可 |
| 倍速守护 | 独立 800ms 轮询，被播放器重置就纠回，并计数 `fixes` |
| 面板显示真实值 | 显示 `video.playbackRate`，与目标不符标红并提示"目标 Nx" |
| 真实时长缺口 | 面板常驻 `真实时长 1:30/4:37 (33%) 差 2:44` |
| 智能降速 | 播完服务端不认，且"进度≥90% 但真实时长<92%" → 判定该倍速不安全，自动降 1x 并记入 `rateUnsafe` |
| 补时按缺口算 | 不再"盲补 2 轮"，而是 `差多少秒补多少秒`，补时期间强制 1x |
| 补时秒表 | 平台 `learnDuration` 每 60s 才刷新，补时阶段用本地秒表把粒度做到 ~2s |

### 所以倍速该怎么用

- **默认 1x**，这是本平台唯一稳的档位。
- 想试 1.25x/1.5x：跑一节，看日志有没有 `倍速守护：…已自动降为 1x`。出现了就说明这档不行，脚本已自动纠正，不用管。
- 没出现且 `__CX.server()` 里该节变 `true`，说明这档服务端认，可以留着。

## 三、v1.3.1：为什么"显示已完成，刷新后又变未完成"

### 证据（`cx-diag-2026-10-21T10-00-16.json`）

页面加载时拉的课程树里，各节的服务端记录：

```
1.1  对象  104/104     3.1  对象   49/49
1.2  对象  251/251     3.2  对象  679/679
...                    3.3  null   —— 一条记录都没有
1.4  对象 2072/2072    3.4  null
```

`isLearned` 是 `null`，不是"时长差一点"，是**服务端压根没这节的记录**。

### 两个原因

**原因 1（我的逻辑错误，主因）：补时判断用错了时长口径**

v1.3.0 里 `topUpDeficit()` 用的是 `realDuration()`，也就是平台在**内存里**累加的 `activeList.isLearned.learnDuration`。这个值跟服务端是否落库无关，永远是"满"的。于是：

```
播完 → 核对返回 false → 算缺口 → 本地算出来是 0 → 判断"时长已够，服务端不认" → 直接跳过
```

**结果就是：明明服务端一条记录都没有，脚本却判定"已够时长"然后往下走。** 你看到的"已完成"，是这一句 `真实时长已够但服务端仍不认，先跳过该节`。

修法：`topUpDeficit()` 改为优先用服务端口径（`S.verify[code].learnDuration`，其次对账台账），拿不到才回退本地。

**原因 2：`insertrecord` 到底有没有落库，以前完全看不见**

平台只有 `insertrecord` 会累计时长（`updatelearncount` 是"浏览量"，跟时长无关，返回 `success:false` 是正常的）。它每 60 秒发一次，body 里 `learnTime→endTime` 就是这一次的上报窗口。

### v1.3.1 新增：落库对账

每次 `insertrecord` 成功返回后 3 秒，回拉一次课程树，比对服务端到底记了多少：

| 面板元素 | 含义 |
|---|---|
| `本地 1:30　服务端 0:00　差 4:14` | 本地内存时长 / 服务端落库时长 / 还差多少 |
| `服务端 无记录 ⚠ 刷新后会变未完成` | 红字，服务端一条都没有 |
| `服务端 已完成 ✓` | 服务端确认 |
| `上报 3/3` | insertrecord 成功次数 / 总次数 |

三种自动报警（每种每节只报一次）：

- `服务端未记录本节（本地已 Xs，服务端无记录）`
- `服务端时长没有增长（本地 Xs，服务端仍 Ys）`
- `服务端比本地落后 Xs，可能在丢上报`

### 补时加了熔断

补时一轮后先看服务端涨没涨：涨了继续，不涨就判定"上报没落库"，立刻停手，不再白耗时间。

```
播完 → 未认可 → 服务端 0s，差 4:14 → 1x 补一轮（约 4 分钟）
     → 再核对 → 服务端仍是 0s → 熔断：上报没有落库，补时无效，跳过
```

### 顺手修掉的两个隐患

- `Player.playing()` 去掉了 `readyState > 2` 判断。缓冲时它会掉到 2，导致每 1.2 秒调一次 `play()`；而平台 `playerPlayCb` 里会 `enterTime = new Date`，上报窗口被切碎，`endTime - learnTime` 变成 0~1 秒，服务端就不累计了。
- `mute()` 加 `!v.muted` 守卫，不再每 tick 调 `setVolume(0)`。

### v1.3.2 补丁（基于 `cx-diag-2026-10-21T10-29-54.json`）

这一轮数据确认了**上报是会落库的**：3.3 从 `isLearned: null` 变成了 `{isLearned:false, learnProgress:60, learnDuration:60}`。

也就是说：机制没问题，**只是每次只累加了 60 秒**。277 秒的课需要累计约 271 秒真实播放，服务端只有 60 秒，自然完不成。

同时 `learnProgress` 也停在 60 —— 说明视频从来没连续播过 3 分钟以上。所以真正要解决的是"别被打断"和"别被跳过"。

| 补丁 | 作用 |
|---|---|
| 播完硬门槛 | 进度必须过 `durationSec × 0.9` 才允许判定播完，防止换源瞬间 `cur/dur` 未就绪被误判 |
| 补时按整窗口 | 服务端按 60 秒窗口累加，补时向上取整到 60 的倍数，且不超过剩余时长 |
| 补时目标改 0.98 | 平台会把 `learnDuration` 截到 `durationSec`，直接按满时长补最稳，避免卡在 0.93 反复失败 |
| `strictComplete` | 服务端不认可的节点**不再静默跳过**，直接暂停并提示 —— 跳过只会让它永远完不成 |
| 窗口体检 | 上报窗口 < 30s 时立刻报警"窗口被切碎，服务端会拒收" |
| 面板补时进度 | 补时阶段显示 `补时 2:00/4:00` |

### v1.3.3：找到真凶 —— 课程树接口被缓存（基于 `cx-diag-2026-10-21T10-38-34.json`）

这一轮数据里，上报终于正常了：

```
insertrecord × 2，delta 都是 60.0s，都返回 success:true
本地进度 179.9，服务端 180  ← 累加是通的
```

但三次拉课程树，**响应体长度一模一样（41899 字节），3.3 的状态全是 `{learnProgress:60, learnDuration:60}`**：

```
10:35:49  页面加载   len=41899   prog=60
10:37:07  第一次对账  len=41899   prog=60   ← 此时本地已经 120
10:38:07  第二次对账  len=41899   prog=60   ← 此时本地已经 180
```

**结论：`GET /api/course/quality/{id}` 被浏览器（或代理）缓存了。** 所以 `verifyNode` 永远读到的是页面加载时的那份快照 —— 无论播多久，服务端"看起来"都停在 60 秒。

这才是"3.3 一直完成不了"的真正原因：不是没上报，不是没累加，而是**核对永远在看旧数据**。

修法：`api()` 对所有 GET 加 `_t=Date.now()` 时间戳，并带 `cache: 'no-store'` + `Cache-Control: no-cache`。

顺带把对账报警放宽成"连续两次不涨才报"，避免服务端落后一个窗口时误报。

### v1.3.4：差 1 秒，以及核对彻底不可用时的兜底（`10-45-25` / `10-46-33`）

**这一轮 3.3 的上报全成功了：**

```
delta 56.1s  → learnProgress 116.1
delta 60.0s  → learnProgress 176.1
delta 60.0s  → learnProgress 236.1
delta 39.9s  → learnProgress 275.9     全部 success:true，累计 216 秒
```

但服务端 3.3 仍是 `{d:60, p:60}`。而且带 `_t=` 时间戳后，5 次课程树请求的响应体 **sha1 完全相同** —— 说明不是浏览器缓存，是服务端这条记录真的没变。

**关键细节：视频停在 275.94 / 277.16。**

`learnProgress 275.9 < 277`，**差 1.2 秒**。而 v1.3.3 的 `completeRatio` 是 0.98，275.99 已经超过 98%，所以脚本判定"时长够了"，既不补时也不报错，直接放行。服务端要的是满 277，差这 1 秒就永远不算。

| 补丁 | 作用 |
|---|---|
| `completeRatio` → **1.0** | 必须补满，差 1 秒也不放过 |
| `finishGap` → **0.05** | 别再提前 0.3 秒就切走 |
| 补时门槛 `def > 5` → **`def > 0.5`** | 差 1 秒也要触发补时 |
| 补时至少播满 60s | 服务端按 60s 窗口累加，播不足一个窗口等于白播 |
| `treeStale` 检测 | 课程树连续 3 次返回同一份数据 → 判定核对不可用，改用本地时长判定，**不阻塞继续** |
| `verifyMode: 'lenient'` | 默认宽松：核对坏了不卡住整门课；改 `'strict'` 则必须服务端认可 |

### v1.3.5：结论确认 —— 完整播一遍就能过（`10-53-08` / `10-53-54`）

你手动把 3.3 从 0:00 播了一遍，5 分钟后：

```
18:53:46  本节播完 4:36/4:37
18:53:50  服务端已确认完成          ← 过了
18:53:50  → 下一节：研究方法
```

服务端最终状态 `{learnDuration: 277, learnProgress: 277, isLearned: true}`。

**这验证了根因：3.3 之前一直卡在 `learnDuration 275.99 / 277`，只差 1 秒。** 完整播一遍后，平台的 `learnDuration += 真实时钟` 顶到了 `durationSec` 上限（277），服务端就认了。

所以 v1.3.5 把补时策略定成：**从头完整播一遍，播到真正的结尾再核对**，不再按"补够多少秒"提前收工 —— 因为缺口可能只有 1 秒，但必须让 `learnDuration` 撞到上限才有效。

| 调整 | 说明 |
|---|---|
| 补时改为整段重播 | 只退出于 `ended`，或用 `durationSec × 2.5` 兜底 |
| `completeRatio: 1.0` | 差 1 秒也不放过 |
| `treeStale` 阈值放宽 | 连续 5 次且本地领先 120s 才判定，避免服务端只是延迟就误判 |

### v1.3.6：3.4 卡住了 —— 播放器被反复 play/pause（`11-59-41` / `12-19-42`）

3.4（1122 秒）跑了 24 分钟只前进了 375 秒。上报记录说明一切：

```
12:09:47  prog 369.8  delta 0
12:11:47  prog 371.3  delta 0
12:13:47  prog 371.3  delta 0
12:15:47  prog 372.9  delta 0
12:17:47  prog 374.6  delta 0
```

两个特征：

1. **视频位置几乎不动** —— 9 分钟前进 5 秒，典型的拉流卡死
2. **每个上报窗口都是 0 毫秒** —— `learnTime` 只比 `endTime` 早 8ms。平台 `playerPlayCb` 里会 `enterTime = new Date`，说明播放器在被反复 play/pause，上报窗口被切成 0，服务端全部丢弃

同时 `learnDuration 671` 远超 `learnProgress 375` —— 时钟在走、画面没动。

| 补丁 | 作用 |
|---|---|
| `Player.play()` / `pause()` 幂等 | 已经在播就绝不碰它，避免每 1.2 秒触发一次 `playerPlayCb` 把 `enterTime` 重置 |
| 去掉 `selfHeal` 的 `seek(cur+1.5)` | 往未缓冲区域 seek 会把 HLS 彻底搞死 |
| 卡顿分级处理 | 30s 提示 + 尝试 play；2 分钟原地重连；8 分钟停机报警 |
| 新增「卡顿中」阶段 | 面板直接显示红色「卡顿中」，不用翻日志 |

**重要：视频卡住时浏览器必须在前台。** Chrome 会把后台标签页的定时器降到 1 分钟一次，HLS 分片加载也被拖慢，视频就会卡死；而 `learnDuration` 照样涨，最后判定不过。

## 五、已确认的平台事实

| 事实 | 证据 |
|---|---|
| 核对接口可能整体失效 | 带 `_t=` 后 5 次响应 sha1 仍完全相同，而本地已 276 |
| 只有 `insertrecord` 累计时长 | `updatelearncount` 是 `addViewCount`（浏览量），返回 `success:false` 属正常 |
| 服务端按真实时间累加 | 成功上报 `endTime-learnTime` 恒为 60.0s |
| `isLearned: null` 表示无记录 | 3.3 是 `null`，而已完成的 1.1~3.2 都是 `{isLearned:true, ...}` |
| 本地 `learnDuration` 不可信 | 平台在内存里 `+= (now-enterTime)/1000`，与是否落库无关 |
| 未作答测验不下发答案 | `hasCompleted:false` 时 `rightAnswer: null` |
| 完成判定看真实时长 | 0.945/0.973 → true，0.812 → false |
| 换节靠 store | 播放器 watch `vid`，`commit('setCourseActiveList', node)` 即换源 |

## 八、流程

```
进入节点
 ├─ isLearned === true              → 直接跳过
 ├─ 进度已满但未认可                → 拉服务端核对
 │    ├─ 认可   → 跳过
 │    ├─ 无记录（已熔断） → 跳过并报警
 │    └─ 未认可 → judgeRate 判倍速 → 1x 从头补时
 └─ 正常播放 → ended → pause 结算 → 等 4s → 核对
      ├─ 认可   → 下一节
      ├─ 未认可 → judgeRate → 按【服务端缺口】1x 补时
      │             ├─ 补够 → 再核对 → 通过则下一节
      │             └─ 服务端时长没涨 → 熔断：上报没落库，跳过并报警
      └─ 拿不到 → 报警，不假装完成
```

补时期间：强制 1x、静音、到结尾自动 seek(0) 循环，按**服务端口径**的缺口播够秒数就收工。
